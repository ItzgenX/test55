The Conditional LoRA Field Guide

This repo (CTRLorALTer / LoRAdapter) teaches Stable Diffusion to follow the shape of a photo — its depth structure — while a text prompt controls everything else. You already know how a neuron and a basic neural net work; everything below builds on exactly that, one small idea at a time, until you can read src/model.py yourself and know what every line is for.

Order matters. Each lesson leans on the ones before it. Two panel types: ▍concept = the idea, plain English. ▍in this repo = the real file that implements it. Running example: the depth-conditioning path — the one wired up by default in this repo.
01Foundation

Numbers in, numbers out

Concept

You already know the core unit: a neuron takes some numbers in, multiplies each by a learned weight, adds them up, and squashes the result through a nonlinearity. A neural network is just many of those, wired together in layers. Everything in this guide — the image encoder, the diffusion model, the LoRA adapters — is that same idea, just organized cleverly and scaled up.

The one habit worth building early: stop picturing "understanding an image" or "generating a picture" as something mysterious. To every network in this repo, a photo is nothing but a grid of numbers — a 512×512 photo is 512 × 512 × 3 (red, green, blue) = 786,432 numbers. A network is a function: numbers go in one end, a lot of multiply-and-add happens in the middle using millions of learned weights, and numbers come out the other end. "Training" nudges those weights so the output gets closer to what you wanted, repeated many thousands of times.

02Foundation

What "latent space" actually is

Concept

786,432 numbers per image is a lot to push through a network thousands of times during training — slow, memory-hungry. So: train one separate, smaller network, once, whose only job is compression — squeeze a photo down into a much smaller grid of numbers that still captures "what this photo looks like," well enough that a second small network can expand it back into (almost) the original photo.

Think of it like describing a face with a short list of dials instead of handing over the whole photograph: "roundness of face: 0.7, eye spacing: 0.3, lighting: warm..." A short list, but a meaningful one — nudge one dial and you get a slightly different, still-plausible face. That's a compressed description, not a random scramble.

That compressed grid is a latent ("hidden" representation). It's called a "space" because similar photos land as nearby points in it, the way similar addresses cluster on a map. The network that learns this compression is a VAE (Variational Autoencoder) — an encoder half (photo → latent) and a decoder half (latent → photo). One detail that matters later: the latent is still a grid, just a smaller one — its top-left still roughly corresponds to the photo's top-left.

In this repo

src/model.py:372-377 — SD15.get_input(), wrapped in @torch.no_grad() (line 363) so no gradients ever flow through the VAE:

03Foundation

Diffusion: destroy the image, then learn to reverse it

Concept

Take a real photo's latent grid (Lesson 2). Add a little random static. Add more. Keep going until it's pure static — nothing recognizable left. That's the forward process, and it isn't learned — it's arithmetic, you choose how much noise to add at each of many steps.

Now train a network to do the reverse: given a noisy latent and "how noisy is this, roughly," guess what noise was just added. If it can always guess correctly, you can subtract that guess, one small step at a time, and walk backwards from pure static to a real image. Generation = start from pure random static and run the reverse process for ~50 steps.

The network making that guess is the UNet — the single most important box in this guide, and the one everything else in this repo modifies. Everything from here on is about what feeds into it and how its own layers get patched.

In this repo

SD15.forward(), src/model.py:419, 475-477, 502 — the "add noise, guess it, compare" loop, one training step:

noisy_latents = self.noise_scheduler.add_noise(latents, noise, timesteps)
model_pred = self.unet(noisy_latents, timesteps,
                        encoder_hidden_states=prompt_embeds).sample
loss = F.mse_loss(model_pred.float(), target.float())

That's the training loop's entire mathematical core. self.noise_scheduler is a DDPMScheduler built from the pipeline's own scheduler config (model.py:115-118) — it decides exactly how much noise "timestep t" means.

04Foundation

The UNet's shape

Concept

Picture a funnel: the network first shrinks the latent grid repeatedly (a coarser, more "global" view each step), then expands it back the same number of times (more precise again). Drawn out, it looks like the letter U — hence "UNet." Each shrink/expand step is a resolution stage.

The shrink side and the expand side are cross-wired with skip connections — fine detail computed on the way down gets handed straight across to the matching stage on the way up, so the network doesn't have to re-invent detail it already had.

Why this matters for us: every place a conditioning signal can attach exists at one specific resolution stage. A signal for the coarse, deep stage means something different than one for the detailed, shallow stage — so a conditioning map has to be produced at all 4 sizes, matched up correctly. That's the whole reason the "mapper" network exists (Lesson 11).

In this repo

The depth numbers on each box above are computed once per patched layer, in add_lora_to_unet, src/model.py:255-260:

if "mid_block" in path:      depth = self.max_depth
elif "down_blocks" in path:  depth = int(path.split("down_blocks.")[1][0])
elif "up_blocks" in path:    depth = self.max_depth - int(path.split("up_blocks.")[1][0])

self.max_depth itself, model.py:120: len(self.pipe.unet.config["block_out_channels"]) - 1 — read straight from the loaded UNet's own config, so this whole scheme adapts automatically to a UNet with a different number of stages (it's exactly how the SDXL path in Lesson 18 reuses the same code). Notice up_blocks depth is mirrored — up_blocks.0 sits right after the bottleneck (depth 3), up_blocks.3 produces the final output (depth 0). This depth number is exactly how each patched layer later knows which of the mapper's 4 outputs belongs to it (Lesson 11).

05Foundation

How the text prompt gets in

Concept

Inside each resolution stage (except the deepest) sits an attention block. Attention lets every "pixel" of the current feature grid look at every word of the prompt and ask "how relevant are you to me right now?" — this is cross-attention, because it's the image attending to text, not to itself. This is the only place text influences the UNet.

Mechanically, attention has query/key/value projections; the two that matter here are to_k and to_v — the layers that actually read the prompt's embeddings. Keep those two names in mind; they come back in Lesson 8 as the target for the style conditioning variant, as opposed to depth's conv-layer target.

In this repo

prompt_embeds — CLIP's encoding of your prompt, tokenized and run through self.text_encoder at src/model.py:390-397 — gets handed straight to the UNet call from Lesson 3:

self.unet(noisy_latents, timesteps, encoder_hidden_states=prompt_embeds)

ATTENTION_MODULES = ["to_k", "to_v"] is declared right at the top of src/model.py:26 — the exact two sub-layer names the LoRA-patching code below looks for whenever it's asked to touch attention instead of convolution.

06Adaptation

Plain LoRA (no diffusion involved yet)

Concept

Say a giant, frozen weight matrix W sits inside a network, and you want to adapt its behavior without touching its (huge, expensive) weights. Trick: leave W completely alone, and add a parallel, much smaller path next to it:

output = W(x)  +  B(A(x))

A shrinks x down to a tiny "rank" (say 128 numbers instead of 1280), B expands it back up. A and B together have far fewer numbers than W, so they're cheap to train and cheap to save. You train only A/B; W never moves. This is standard LoRA — nothing repo-specific yet.

In this repo

The entire pretrained UNet is frozen before any LoRA is even added — src/model.py:125:

self.unet.requires_grad_(False)

NewStructLoRAConv in src/lora.py:164-172 builds exactly the textbook form above: self.W a frozen Conv2d (requires_grad_(False) right after creation), self.A a rank-sized down-projection conv, self.B a 1×1 up-projection conv, B's weights zero-initialized so the adapter starts as a no-op.

07The core idea

Making the LoRA conditional (FiLM)

Concept

Plain LoRA's B(A(x)) behaves identically no matter which image you're generating — a fixed, static edit. What if you want the edit to change depending on some extra input — "bend the output towards matching THIS depth map"? The correction needs to be a function of that extra signal, not a constant.

The standard trick is FiLM (Feature-wise Linear Modulation): compute a per-pixel scale and shift from your conditioning signal, and apply them as scale × activation + shift somewhere inside the network. Two small layers, conventionally gamma (→ scale) and beta (→ shift), turn your conditioning map into those numbers.

This one idea — modulate the LoRA's internal activation using a conditioning signal, instead of leaving it alone — is the entire novelty of this paper. Everything else you've read so far (frozen weight, low-rank path, UNet shape) is standard machinery this idea gets bolted onto.

In this repo

NewStructLoRAConv.forward(), src/lora.py:177-197 — the class used for depth/structure conditioning:

w_out = self.W(x)                                    # frozen conv, untouched
cs = self.data_provider.get_batch()                   # tuple of 4 maps (Lesson 12)
c = cs[self.depth]                                     # THIS layer's matching-resolution map
element_shift = self.beta(c)                           # 1x1 conv: c -> per-pixel shift
element_scale = self.gamma(c) + 1.0                     # 1x1 conv: c -> per-pixel scale
a_out = self.A(x)                                       # low-rank down-projection
a_cond = a_out * element_scale + element_shift           # <-- FiLM, right here
b_out = self.B(a_cond)                                  # low-rank up-projection
return w_out + b_out * self.lora_scale

Every other line matches Lesson 6's plain LoRA exactly. Only the a_cond = ... line is new. self.gamma and self.beta are declared at lora.py:174-175 as plain 1×1 convolutions, no bias.

08Architecture

09Depth, in depth

The depth encoder, start to finish

Concept

Before a conditioning map can reach the c in Lesson 7, a raw photo has to become a canonical map — something meaningful, same rough shape as the input, not just pixels. For structure conditioning, that canonical map is a depth map: for every pixel, roughly "how far away is this."

This repo doesn't train its own depth network. It reuses MiDaS (specifically the DPT-Hybrid variant) — a depth estimator someone else already trained on millions of photos, kept entirely frozen, purely as a feature extractor. You never see "depth" as a separate label in a dataset folder anywhere in this pipeline; it's produced live, every step, by running this frozen network.

In this repo

DepthEstimator, src/annotators/midas.py:14-64, wraps Intel/dpt-hybrid-midas via HuggingFace transformers (midas.py:27), frozen and in eval mode (midas.py:30-31). Its forward() does exactly four things, in order:

imgs = (imgs + 1.0) / 2.0                 # [-1,1] -> [0,1], MiDaS's expected range
imgs = better_resize(imgs, self.model_size)  # crop+resize to MiDaS's own 384x384 input
depth_map = self.depth_estimator(pixel_values=imgs).predicted_depth
depth_map = F.interpolate(depth_map.unsqueeze(1), size=(self.size, self.size),
                           mode="bicubic")            # up/down to this run's target size
# then: per-image min-max normalize to [0,1], and repeat to 3 channels

better_resize, src/annotators/util.py:9-28, is the same small utility used to feed every vision encoder in this repo: center-crop to a square using the shorter side, average-pool down if the crop is much bigger than the target (anti-aliased, not just a naive resize), then bilinear-interpolate to the exact target size.

The min-max step (midas.py:58-60) matters: MiDaS outputs relative depth in arbitrary units, so each image's depth map is independently rescaled so its own nearest point is 0 and its own farthest point is 1 — there is no shared "meters" scale across images, only per-image relative structure. The final torch.cat([depth_map] * 3, dim=1) (midas.py:61) triples the single depth channel into 3 identical channels purely so the shape matches what the mapper (Lesson 11) expects — an RGB-shaped tensor, even though there's no color information in it at all.

Contract, confirmed by reading the code, not assumed: input [B, 3, H, W] float in [-1, 1]; output [B, 3, size, size] float in [0, 1], where size comes from the run's Hydra config (configs/lora/encoder/midas.yaml:6: size: ${size}).

10The trick

No depth dataset needed — it reads its own target

Concept

Here's the detail that makes the whole depth-conditioning setup click: during training, the depth map for image X is computed from image X itself — the exact same photo the diffusion model is being asked to reconstruct. There is no separate "depth" column in the dataset. The pipeline hands the frozen MiDaS network the training photo, gets a depth map back on the spot, and uses that as the conditioning signal for reconstructing that same photo.

Why that's the right call, not a shortcut: it means any folder of plain photos is trainable data — nothing needs to be pre-labelled with depth. And because the depth encoder is frozen and deterministic, the model can't "cheat" by ignoring the depth map — the depth map and the target photo are, by construction, perfectly consistent with each other every single step.

At generation time this flips into the actual product: you hand the model a real reference photo, it live-extracts that photo's depth structure the same way, and the diffusion process generates a new image — different content, different style, whatever the prompt says — constrained to follow that same depth structure. That's the "0-Shot Control" in this repo's name: no retraining needed to condition on a new photo's structure.

In this repo

train.py:143-148 — the training batch's own images are reused as the conditioning input, once per active LoRA:

imgs = batch["jpg"]
imgs = imgs.to(accelerator.device)
imgs = imgs.clip(-1.0, 1.0)
cs = [imgs] * n_loras          # same photo, handed to every conditioning encoder

Then inside SD15.forward(), model.py:454-472, that same tensor (named lora_c there) is what the depth encoder actually sees:

for i, (encoder, dp, mapper, lora_c) in enumerate(zip(encoders, self.dps, mappers, cs)):
    ...
    cond = encoder(lora_c)      # depth map, extracted from THIS SAME training image
    mapped_cond = mapper(cond)
    dp.set_batch(mapped_cond)

Meanwhile latents — what the UNet is being trained to denoise back into — was built from that identical imgs tensor back in Lesson 2's VAE step. Same photo, two uses: ground truth to reconstruct, and (via MiDaS) the structural hint telling the model what shape that reconstruction should take. The validation logging code confirms this is treated as a real, inspectable signal, not an incidental side effect — train.py:225-227: if cfg.get("log_c", False): lp = model.encoders[0](cs[-1]).cpu() literally re-runs the depth encoder just to save the depth map image to TensorBoard.

11Depth, in depth

One map, four resolutions: the mapper

Concept

The depth map from Lesson 9 is one flat grid at one resolution. But Lesson 4 showed the UNet has 4 stages at 4 different sizes — a signal meant for the 64×64 stage is the wrong shape for the 8×8 stage. So a small trainable CNN, the mapper, takes the one depth map in and produces four versions of it, each already at the right resolution for one UNet stage. Unlike the depth estimator, the mapper is not frozen — it's trained from scratch alongside the LoRA adapters, learning how to best translate "depth" into "a FiLM-friendly per-layer signal."

In this repo

FixedStructureMapper15, src/mapper_network.py:18-82, is a plain stride-2 downsampling CNN with a 1×1 conv "tap" at each stop. For a 512×512 input, computed directly from the strides in the code (not assumed): self.down has three stride-2 convs (512→256→128→64), then block1/block2/block3 each halve again — 64→32→16→8. Four stopping points, four 1×1 Conv2d(128, c_dim) taps (out0..out3, mapper_network.py:64-67), each producing a c_dim-channel (128 by default) map at exactly one of those four sizes — 64, 32, 16, 8 — the same four numbers as Fig. 2's UNet stages, by construction rather than coincidence.

def forward(self, x, *args, **kwargs):
    base = self.down(x)                 # 512 -> 64
    b0 = self.block0(base)              # identity, stays 64
    b1 = self.block1(b0)                # 64 -> 32
    b2 = self.block2(b1)                # 32 -> 16
    b3 = self.block3(b2)                # 16 -> 8
    return self.out0(b0), self.out1(b1), self.out2(b2), self.out3(b3)

One forward pass through the whole encoder→mapper chain, model.py:470-472:

cond = encoder(lora_c)          # depth map, [B,3,512,512]
mapped_cond = mapper(cond)      # tuple of FOUR tensors, one per UNet stage
dp.set_batch(mapped_cond)       # DataProvider now holds all 4 (Lesson 12)
12Depth, in depth

The DataProvider mailbox

Concept

The mapper runs once per training step and produces all 4 resolution maps at once. But dozens of individual conv layers, scattered across the UNet, each need to read their own matching map during the UNet's single forward pass. Rather than threading that tuple through every layer's function call, the codebase uses a tiny shared object — set once at the top, read from many places below — as a mailbox.

In this repo

DataProvider, src/utils.py:18-35, is intentionally dumb — no logic beyond a getter and setter:

class DataProvider:
    def set_batch(self, batch): self.batch = batch
    def get_batch(self):
        assert self.batch is not None, "Error: need to set a batch first"
        return self.batch

Each conditioning source (depth here) gets its own DataProvider instance, created once in add_lora_from_config (utils.py:63) and handed by reference to every patched layer for that source when they're constructed (model.py:271-272, 292: data_provider=data_provider). Lesson 11's dp.set_batch(mapped_cond) fills the mailbox once per step; Lesson 7's cs = self.data_provider.get_batch() is every individual conv layer reading from that same mailbox and picking out its own [self.depth] slot. One write, many reads — that's the entire pattern.

13Depth, in depth

Swapping the encoder: same slot, different input

Concept

Look again at Lesson 9's contract: the mapper doesn't care what kind of map it receives, only its shape and value range — [B, 3, H, W] float in a fixed range. Any frozen network satisfying that contract can sit in the encoder slot. This repo doesn't just claim that in the abstract — it ships more than one.

In this repo

src/annotators/ holds several interchangeable encoders, each wrapped to the same rough in/out shape:

  • midas.py — DepthEstimator: this guide's running example, depth structure (Lesson 9).
  • canny.py — CannyDetector: classic OpenCV edge detection, no learned weights at all — cv2.Canny per image, thresholded and channel-repeated to match the same 3-channel shape.
  • hed.py — TorchHEDdetector: a small pretrained edge-detection CNN (ControlNetHED_Apache2), frozen, producing softer, more holistic edge maps than Canny.
  • style.py / openclip.py — VisionModel: not a spatial map at all — a single pooled CLIP image-embedding vector, used by the style conditioning path (configs/lora/style.yaml, Lesson 8's third row) instead of depth's per-pixel map.

Which one loads is a one-line Hydra swap — compare configs/lora/encoder/midas.yaml (_target_: src.annotators.midas.DepthEstimator) against configs/lora/encoder/canny.yaml or hed.yaml — same mount point in configs/lora/struct.yaml's encoder: ??? default, a different Python class instantiated underneath. Everything downstream — mapper, DataProvider, FiLM math, layer targeting — is unchanged, because none of it was ever written to know what "depth" specifically means; it only knows tensor shapes.

14Running the repo

Hydra: how a dozen yaml files become one Python object

Concept

Every knob you've seen so far — adaption_mode, which encoder, image size, learning rate — lives in a small yaml file, not scattered through Python code. Hydra is the library that stitches many small yaml files into one merged config tree at startup, then (in this repo) turns that tree straight into live Python objects.

Three ideas make the whole system click:

  • Config groups — a folder of interchangeable yaml files, like configs/model/ holding both sd15.yaml and sdxl.yaml. Only one file from a group is active per run.
  • Defaults list — each yaml's own defaults: block says which file from each group it wants, or ??? to mean "you must supply one." An override entry lets a more specific config swap out a choice a more general one already made.
  • _target_ + instantiate — any yaml dict with a _target_ key names a real Python import path. hydra.utils.instantiate(cfg) walks the whole merged tree and actually constructs every such object, innermost first, wiring constructor arguments straight from the surrounding yaml keys.

In this repo

The root config, configs/train.yaml:1-5, declares the mandatory groups and leaves room for an experiment file to override everything:

defaults:
  - data: ???
  - model: ???
  - _self_
  - experiment: null

An experiment file, e.g. configs/experiment/train_struct_sd15.yaml:1-9, starts with # @package _global_ (its keys merge straight into the top-level config, not nested under experiment:) and picks concrete choices for every group in one place:

defaults:
  - /lora@lora.struct: struct                          # mount configs/lora/struct.yaml at cfg.lora.struct
  - override /lora/encoder@lora.struct.encoder: midas   # fill struct.yaml's encoder: ??? with midas.yaml
  - override /model: sd15
  - override /data: local

Running python train.py experiment=train_struct_sd15 (or, for sampling, exactly the README's python sample.py experiment=sample_struct pattern) tells Hydra to load that one experiment file on top of train.yaml/sample.yaml. Each individual leaf yaml carries a _target_ — configs/model/sd15.yaml:4: _target_: src.model.SD15, configs/lora/encoder/midas.yaml:4: _target_: src.annotators.midas.DepthEstimator. train.py:54's single line cfg = hydra.utils.instantiate(cfg) turns the entire merged tree of yaml into real, already-constructed SD15, DepthEstimator, and FixedStructureMapper15 instances — after that line, cfg.model genuinely is a live PyTorch module, not a dict describing one. Interpolations like midas.yaml's size: ${size} pull from the one size: value set higher up (train_struct_sd15.yaml:22: size: 512) — a single source of truth shared across model, encoder, and data config, instead of three copies that could silently drift apart.

15Running the repo

Code flow: training, step by step

Concept

With every earlier lesson's pieces named, train.py reads as a straight-line story: build the model, attach the LoRA(s), loop over the data, and every so often generate a sample image to check progress.

In this repo

  1. Compose & instantiate (train.py:33-58) — Hydra loads the config (Lesson 14), instantiate builds the real SD15 model, moved to the accelerator's device.
  2. Attach LoRAs (train.py:61, delegating to utils.py:48-112 add_lora_from_config) — for each entry under cfg.lora (here, just struct), build a fresh DataProvider, call model.add_lora_to_unet (Lesson 8's layer-swap), and optionally load an existing checkpoint.
  3. Optimizer (train.py:71-86) — one AdamW over three parameter groups: the LoRA A/B/gamma/beta weights (model.params_to_optimize), the mapper's weights, and (if unfrozen) the encoder's weights. self.unet.requires_grad_(False) from Lesson 6 means the base UNet weights never appear here.
  4. Per-step training (train.py:141-168) — pull a batch, build cs = [imgs] * n_loras (Lesson 10), call model.forward_easy(imgs, prompts, cs, ...) which internally does everything from Lessons 2, 3, 7, 9, 11, 12 in one pass, then accelerator.backward(loss) and an optimizer step.
  5. Periodic validation (train.py:179-282, every cfg.val_steps) — switch to eval mode, run real image generation (Lesson 16's sampling path) on a few held-out batches, log the generated images plus the conditioning map itself to TensorBoard, then save a checkpoint via utils.py:136-144 save_checkpoint before resuming training.
16Running the repo

Code flow: sampling, step by step

Concept

sample.py is the script the README's python sample.py experiment=... usage actually runs. It's shorter than training because there's no loss, no backward pass, no optimizer — just: load a trained checkpoint, feed it real conditioning images, save the outputs.

In this repo

  1. Compose, instantiate, load checkpoint (sample.py:41-65) — same Hydra/instantiate pattern as training, plus add_lora_from_config now actually finding a ckpt_path and loading real trained weights into the swapped-in LoRA layers and mapper (utils.py:88-104).
  2. Freeze for inference (sample.py:84-85) — unet.requires_grad_(False); unet.eval().
  3. Per-batch sampling (sample.py:94-132) — pull a conditioning image from the val dataloader, build cs = [imgs for _ in model.mappers] (Lesson 10's live-extraction trick, now on whatever reference photo you supplied), then model.sample(**pipeline_args).
  4. SD15.sample_easy (model.py:649-713) — for each conditioning source, doubles the map into a [zeros, real_map] pair (Lesson 17's classifier-free guidance), runs the encoder+mapper+DataProvider chain once, then calls self.pipe(...) — diffusers's own multi-step denoising loop, which repeatedly calls the now-patched UNet exactly as in training, just without gradients and for ~50 steps starting from pure noise.
  5. Save outputs (sample.py:131-143) — each generated image and its input conditioning image are written to disk side by side, so you can directly compare "the depth I asked for" against "the depth the output actually has."
17Running the repo

Why conditioning gets randomly dropped

Concept

If a model is always shown a prompt and always shown a depth map, it never learns what to do without them — and at generation time you often want to dial the strength of conditioning up or down, not just have it fully on. The standard fix is classifier-free guidance (CFG): during training, randomly blank out the condition some small fraction of the time, so the network also learns the "no condition" case. At generation time, run the model twice per step — once with the real condition, once with it blanked — and push the output away from the unconditioned guess and towards the conditioned one, by a tunable amount. That amount is the familiar "guidance scale" slider.

In this repo

Two independent dropout sites, both controlled by c_dropout (default 0.05, model.py:60). Text prompt dropout, model.py:380:

prompts = ["" if random.random() < self.c_dropout else p for p in prompts]

Depth-map dropout, per conditioning source, model.py:456-459:

dropout_mask = torch.rand(bsz, device=lora_c.device) < self.c_dropout
lora_c[dropout_mask] = torch.zeros_like(lora_c[dropout_mask])

At generation time, sample_custom, model.py:580-586, 626-627, builds the paired batch and combines the two predictions:

SDXL and B-LoRA: the same mechanism, reused

Concept

Every lesson above uses Stable Diffusion 1.5 as the concrete example, but nothing about the conditional-LoRA mechanism is SD1.5-specific — it only needed a UNet with named, path-addressable layers and a handful of resolution stages. This repo also ships a second full model class for SDXL, a larger UNet with the same fundamental shape (just bigger, and with an extra pooled/time conditioning input), reusing the exact same add_lora_to_unet layer-matching code from Lesson 8.

In this repo

SDXL(ModelBase), src/model.py:716-935, mirrors SD15's structure — same frozen-UNet setup, same LoRA-patching call — with SDXL's extra pooled-embedding and time-id conditioning threaded through get_conditioning (model.py:735-775). Its matching mapper, FixedStructureMapperXL (mapper_network.py:85-131), produces three taps instead of four — SDXL's UNet only has 3 resolution stages, one fewer than SD1.5's 4.

Separately, this repo implements B-LoRA's content/style disentanglement as two more adaption_mode values, model.py:202-213: b-lora_content targets only up_blocks.0.attentions.0, b-lora_style only up_blocks.0.attentions.1 — two specific attention blocks that prior research found separately encode an image's content versus its style. configs/experiment/sample_b-lora_sdxl.yaml wires this up on SDXL directly; setting adaption_mode to just one of the two lets you condition on only content or only style from a reference image, per the README's usage note.
