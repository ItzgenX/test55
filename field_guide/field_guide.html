The Conditional LoRA Field Guide

This repo (CTRLorALTer / LoRAdapter) teaches Stable Diffusion to follow the shape of a photo — depth structure, or now segmentation structure — while a text prompt controls everything else. You already know how a neuron and a basic neural net work; everything below builds on exactly that, one small idea at a time, until you can read src/model.py yourself and know what every line is for.

Order matters. Each lesson leans on the ones before it. Updated in place. Lessons 19–24 are this session's own segmentation work — same rule: every claim grounded in a real file read this session. Two panel types: ▍concept = the idea, plain English. ▍in this repo = the real file that implements it. Running example: the depth-conditioning path — the one wired up by default in this repo.
01Foundation

Numbers in, numbers out

Concept

You already know the core unit: a neuron takes some numbers in, multiplies each by a learned weight, adds them up, and squashes the result through a nonlinearity. A neural network is just many of those, wired together in layers. Everything in this guide — the image encoder, the diffusion model, the LoRA adapters — is that same idea, just organized cleverly and scaled up.

The one habit worth building early: stop picturing "understanding an image" or "generating a picture" as something mysterious. To every network in this repo, a photo is nothing but a grid of numbers — a 512×512 photo is 512 × 512 × 3 (red, green, blue) = 786,432 numbers. A network is a function: numbers go in one end, a lot of multiply-and-add happens in the middle using millions of learned weights, and numbers come out the other end. "Training" nudges those weights so the output gets closer to what you wanted, repeated many thousands of times.

02Foundation

What "latent space" actually is

Concept

786,432 numbers per image is a lot to push through a network thousands of times during training — slow, memory-hungry. So: train one separate, smaller network, once, whose only job is compression — squeeze a photo down into a much smaller grid of numbers that still captures "what this photo looks like," well enough that a second small network can expand it back into (almost) the original photo.

Think of it like describing a face with a short list of dials instead of handing over the whole photograph: "roundness of face: 0.7, eye spacing: 0.3, lighting: warm..." A short list, but a meaningful one — nudge one dial and you get a slightly different, still-plausible face. That's a compressed description, not a random scramble.

That compressed grid is a latent ("hidden" representation). It's called a "space" because similar photos land as nearby points in it, the way similar addresses cluster on a map. The network that learns this compression is a VAE (Variational Autoencoder) — an encoder half (photo → latent) and a decoder half (latent → photo). One detail that matters later: the latent is still a grid, just a smaller one — its top-left still roughly corresponds to the photo's top-left.

In this repo

src/model.py:372-377 — SD15.get_input(), wrapped in @torch.no_grad() (line 363) so no gradients ever flow through the VAE:

03Foundation

Diffusion: destroy the image, then learn to reverse it

Concept

Take a real photo's latent grid (Lesson 2). Add a little random static. Add more. Keep going until it's pure static — nothing recognizable left. That's the forward process, and it isn't learned — it's arithmetic, you choose how much noise to add at each of many steps.

Now train a network to do the reverse: given a noisy latent and "how noisy is this, roughly," guess what noise was just added. If it can always guess correctly, you can subtract that guess, one small step at a time, and walk backwards from pure static to a real image. Generation = start from pure random static and run the reverse process for ~50 steps.

The network making that guess is the UNet — the single most important box in this guide, and the one everything else in this repo modifies. Everything from here on is about what feeds into it and how its own layers get patched.

In this repo

SD15.forward(), src/model.py:419, 475-477, 502 — the "add noise, guess it, compare" loop, one training step:

noisy_latents = self.noise_scheduler.add_noise(latents, noise, timesteps)
model_pred = self.unet(noisy_latents, timesteps,
                        encoder_hidden_states=prompt_embeds).sample
loss = F.mse_loss(model_pred.float(), target.float())

That's the training loop's entire mathematical core. self.noise_scheduler is a DDPMScheduler built from the pipeline's own scheduler config (model.py:115-118) — it decides exactly how much noise "timestep t" means.

04Foundation

The UNet's shape

Concept

Picture a funnel: the network first shrinks the latent grid repeatedly (a coarser, more "global" view each step), then expands it back the same number of times (more precise again). Drawn out, it looks like the letter U — hence "UNet." Each shrink/expand step is a resolution stage.

The shrink side and the expand side are cross-wired with skip connections — fine detail computed on the way down gets handed straight across to the matching stage on the way up, so the network doesn't have to re-invent detail it already had.

Why this matters for us: every place a conditioning signal can attach exists at one specific resolution stage. A signal for the coarse, deep stage means something different than one for the detailed, shallow stage — so a conditioning map has to be produced at all 4 sizes, matched up correctly. That's the whole reason the "mapper" network exists (Lesson 11).

In this repo

The depth numbers on each box above are computed once per patched layer, in add_lora_to_unet, src/model.py:255-260:

if "mid_block" in path:      depth = self.max_depth
elif "down_blocks" in path:  depth = int(path.split("down_blocks.")[1][0])
elif "up_blocks" in path:    depth = self.max_depth - int(path.split("up_blocks.")[1][0])

self.max_depth itself, model.py:120: len(self.pipe.unet.config["block_out_channels"]) - 1 — read straight from the loaded UNet's own config, so this whole scheme adapts automatically to a UNet with a different number of stages (it's exactly how the SDXL path in Lesson 18 reuses the same code). Notice up_blocks depth is mirrored — up_blocks.0 sits right after the bottleneck (depth 3), up_blocks.3 produces the final output (depth 0). This depth number is exactly how each patched layer later knows which of the mapper's 4 outputs belongs to it (Lesson 11).

05Foundation

How the text prompt gets in

Concept

Inside each resolution stage (except the deepest) sits an attention block. Attention lets every "pixel" of the current feature grid look at every word of the prompt and ask "how relevant are you to me right now?" — this is cross-attention, because it's the image attending to text, not to itself. This is the only place text influences the UNet.

Mechanically, attention has query/key/value projections; the two that matter here are to_k and to_v — the layers that actually read the prompt's embeddings. Keep those two names in mind; they come back in Lesson 8 as the target for the style conditioning variant, as opposed to depth's conv-layer target.

In this repo

prompt_embeds — CLIP's encoding of your prompt, tokenized and run through self.text_encoder at src/model.py:390-397 — gets handed straight to the UNet call from Lesson 3:

self.unet(noisy_latents, timesteps, encoder_hidden_states=prompt_embeds)

ATTENTION_MODULES = ["to_k", "to_v"] is declared right at the top of src/model.py:26 — the exact two sub-layer names the LoRA-patching code below looks for whenever it's asked to touch attention instead of convolution.

06Adaptation

Plain LoRA (no diffusion involved yet)

Concept

Say a giant, frozen weight matrix W sits inside a network, and you want to adapt its behavior without touching its (huge, expensive) weights. Trick: leave W completely alone, and add a parallel, much smaller path next to it:

output = W(x)  +  B(A(x))

A shrinks x down to a tiny "rank" (say 128 numbers instead of 1280), B expands it back up. A and B together have far fewer numbers than W, so they're cheap to train and cheap to save. You train only A/B; W never moves. This is standard LoRA — nothing repo-specific yet.

In this repo

The entire pretrained UNet is frozen before any LoRA is even added — src/model.py:125:

self.unet.requires_grad_(False)

NewStructLoRAConv in src/lora.py:164-172 builds exactly the textbook form above: self.W a frozen Conv2d (requires_grad_(False) right after creation), self.A a rank-sized down-projection conv, self.B a 1×1 up-projection conv, B's weights zero-initialized so the adapter starts as a no-op.

07The core idea

Making the LoRA conditional (FiLM)

Concept

Plain LoRA's B(A(x)) behaves identically no matter which image you're generating — a fixed, static edit. What if you want the edit to change depending on some extra input — "bend the output towards matching THIS depth map"? The correction needs to be a function of that extra signal, not a constant.

The standard trick is FiLM (Feature-wise Linear Modulation): compute a per-pixel scale and shift from your conditioning signal, and apply them as scale × activation + shift somewhere inside the network. Two small layers, conventionally gamma (→ scale) and beta (→ shift), turn your conditioning map into those numbers.

This one idea — modulate the LoRA's internal activation using a conditioning signal, instead of leaving it alone — is the entire novelty of this paper. Everything else you've read so far (frozen weight, low-rank path, UNet shape) is standard machinery this idea gets bolted onto.

In this repo

NewStructLoRAConv.forward(), src/lora.py:177-197 — the class used for depth/structure conditioning:

w_out = self.W(x)                                    # frozen conv, untouched
cs = self.data_provider.get_batch()                   # tuple of 4 maps (Lesson 12)
c = cs[self.depth]                                     # THIS layer's matching-resolution map
element_shift = self.beta(c)                           # 1x1 conv: c -> per-pixel shift
element_scale = self.gamma(c) + 1.0                     # 1x1 conv: c -> per-pixel scale
a_out = self.A(x)                                       # low-rank down-projection
a_cond = a_out * element_scale + element_shift           # <-- FiLM, right here
b_out = self.B(a_cond)                                  # low-rank up-projection
return w_out + b_out * self.lora_scale

Every other line matches Lesson 6's plain LoRA exactly. Only the a_cond = ... line is new. self.gamma and self.beta are declared at lora.py:174-175 as plain 1×1 convolutions, no bias.

09Depth, in depth

The depth encoder, start to finish

Concept

Before a conditioning map can reach the c in Lesson 7, a raw photo has to become a canonical map — something meaningful, same rough shape as the input, not just pixels. For structure conditioning, that canonical map is a depth map: for every pixel, roughly "how far away is this."

This repo doesn't train its own depth network. It reuses MiDaS (specifically the DPT-Hybrid variant) — a depth estimator someone else already trained on millions of photos, kept entirely frozen, purely as a feature extractor. You never see "depth" as a separate label in a dataset folder anywhere in this pipeline; it's produced live, every step, by running this frozen network.

In this repo

DepthEstimator, src/annotators/midas.py:14-64, wraps Intel/dpt-hybrid-midas via HuggingFace transformers (midas.py:27), frozen and in eval mode (midas.py:30-31). Its forward() does exactly four things, in order:

imgs = (imgs + 1.0) / 2.0                 # [-1,1] -> [0,1], MiDaS's expected range
imgs = better_resize(imgs, self.model_size)  # crop+resize to MiDaS's own 384x384 input
depth_map = self.depth_estimator(pixel_values=imgs).predicted_depth
depth_map = F.interpolate(depth_map.unsqueeze(1), size=(self.size, self.size),
                           mode="bicubic")            # up/down to this run's target size
# then: per-image min-max normalize to [0,1], and repeat to 3 channels

better_resize, src/annotators/util.py:9-28, is the same small utility used to feed every vision encoder in this repo: center-crop to a square using the shorter side, average-pool down if the crop is much bigger than the target (anti-aliased, not just a naive resize), then bilinear-interpolate to the exact target size.

The min-max step (midas.py:58-60) matters: MiDaS outputs relative depth in arbitrary units, so each image's depth map is independently rescaled so its own nearest point is 0 and its own farthest point is 1 — there is no shared "meters" scale across images, only per-image relative structure. The final torch.cat([depth_map] * 3, dim=1) (midas.py:61) triples the single depth channel into 3 identical channels purely so the shape matches what the mapper (Lesson 11) expects — an RGB-shaped tensor, even though there's no color information in it at all.

Contract, confirmed by reading the code, not assumed: input [B, 3, H, W] float in [-1, 1]; output [B, 3, size, size] float in [0, 1], where size comes from the run's Hydra config (configs/lora/encoder/midas.yaml:6: size: ${size}).

10The trick

No depth dataset needed — it reads its own target

Concept

Here's the detail that makes the whole depth-conditioning setup click: during training, the depth map for image X is computed from image X itself — the exact same photo the diffusion model is being asked to reconstruct. There is no separate "depth" column in the dataset. The pipeline hands the frozen MiDaS network the training photo, gets a depth map back on the spot, and uses that as the conditioning signal for reconstructing that same photo.

Why that's the right call, not a shortcut: it means any folder of plain photos is trainable data — nothing needs to be pre-labelled with depth. And because the depth encoder is frozen and deterministic, the model can't "cheat" by ignoring the depth map — the depth map and the target photo are, by construction, perfectly consistent with each other every single step.

At generation time this flips into the actual product: you hand the model a real reference photo, it live-extracts that photo's depth structure the same way, and the diffusion process generates a new image — different content, different style, whatever the prompt says — constrained to follow that same depth structure. That's the "0-Shot Control" in this repo's name: no retraining needed to condition on a new photo's structure.

In this repo

train.py:143-148 — the training batch's own images are reused as the conditioning input, once per active LoRA:

imgs = batch["jpg"]
imgs = imgs.to(accelerator.device)
imgs = imgs.clip(-1.0, 1.0)
cs = [imgs] * n_loras          # same photo, handed to every conditioning encoder

Then inside SD15.forward(), model.py:454-472, that same tensor (named lora_c there) is what the depth encoder actually sees:

for i, (encoder, dp, mapper, lora_c) in enumerate(zip(encoders, self.dps, mappers, cs)):
    ...
    cond = encoder(lora_c)      # depth map, extracted from THIS SAME training image
    mapped_cond = mapper(cond)
    dp.set_batch(mapped_cond)

Meanwhile latents — what the UNet is being trained to denoise back into — was built from that identical imgs tensor back in Lesson 2's VAE step. Same photo, two uses: ground truth to reconstruct, and (via MiDaS) the structural hint telling the model what shape that reconstruction should take. The validation logging code confirms this is treated as a real, inspectable signal, not an incidental side effect — train.py:225-227: if cfg.get("log_c", False): lp = model.encoders[0](cs[-1]).cpu() literally re-runs the depth encoder just to save the depth map image to TensorBoard.

11Depth, in depth

One map, four resolutions: the mapper

Concept

The depth map from Lesson 9 is one flat grid at one resolution. But Lesson 4 showed the UNet has 4 stages at 4 different sizes — a signal meant for the 64×64 stage is the wrong shape for the 8×8 stage. So a small trainable CNN, the mapper, takes the one depth map in and produces four versions of it, each already at the right resolution for one UNet stage. Unlike the depth estimator, the mapper is not frozen — it's trained from scratch alongside the LoRA adapters, learning how to best translate "depth" into "a FiLM-friendly per-layer signal."

In this repo

FixedStructureMapper15, src/mapper_network.py:18-82, is a plain stride-2 downsampling CNN with a 1×1 conv "tap" at each stop. For a 512×512 input, computed directly from the strides in the code (not assumed): self.down has three stride-2 convs (512→256→128→64), then block1/block2/block3 each halve again — 64→32→16→8. Four stopping points, four 1×1 Conv2d(128, c_dim) taps (out0..out3, mapper_network.py:64-67), each producing a c_dim-channel (128 by default) map at exactly one of those four sizes — 64, 32, 16, 8 — the same four numbers as Fig. 2's UNet stages, by construction rather than coincidence.

def forward(self, x, *args, **kwargs):
    base = self.down(x)                 # 512 -> 64
    b0 = self.block0(base)              # identity, stays 64
    b1 = self.block1(b0)                # 64 -> 32
    b2 = self.block2(b1)                # 32 -> 16
    b3 = self.block3(b2)                # 16 -> 8
    return self.out0(b0), self.out1(b1), self.out2(b2), self.out3(b3)

One forward pass through the whole encoder→mapper chain, model.py:470-472:

cond = encoder(lora_c)          # depth map, [B,3,512,512]
mapped_cond = mapper(cond)      # tuple of FOUR tensors, one per UNet stage
dp.set_batch(mapped_cond)       # DataProvider now holds all 4 (Lesson 12)
12Depth, in depth

The DataProvider mailbox

Concept

The mapper runs once per training step and produces all 4 resolution maps at once. But dozens of individual conv layers, scattered across the UNet, each need to read their own matching map during the UNet's single forward pass. Rather than threading that tuple through every layer's function call, the codebase uses a tiny shared object — set once at the top, read from many places below — as a mailbox.

In this repo

DataProvider, src/utils.py:18-35, is intentionally dumb — no logic beyond a getter and setter:

class DataProvider:
    def set_batch(self, batch): self.batch = batch
    def get_batch(self):
        assert self.batch is not None, "Error: need to set a batch first"
        return self.batch

Each conditioning source (depth here) gets its own DataProvider instance, created once in add_lora_from_config (utils.py:63) and handed by reference to every patched layer for that source when they're constructed (model.py:271-272, 292: data_provider=data_provider). Lesson 11's dp.set_batch(mapped_cond) fills the mailbox once per step; Lesson 7's cs = self.data_provider.get_batch() is every individual conv layer reading from that same mailbox and picking out its own [self.depth] slot. One write, many reads — that's the entire pattern.

13Depth, in depth

Swapping the encoder: same slot, different input

Concept

Look again at Lesson 9's contract: the mapper doesn't care what kind of map it receives, only its shape and value range — [B, 3, H, W] float in a fixed range. Any frozen network satisfying that contract can sit in the encoder slot. This repo doesn't just claim that in the abstract — it ships more than one.

In this repo

src/annotators/ holds several interchangeable encoders, each wrapped to the same rough in/out shape:

  • midas.py — DepthEstimator: this guide's running example, depth structure (Lesson 9).
  • canny.py — CannyDetector: classic OpenCV edge detection, no learned weights at all — cv2.Canny per image, thresholded and channel-repeated to match the same 3-channel shape.
  • hed.py — TorchHEDdetector: a small pretrained edge-detection CNN (ControlNetHED_Apache2), frozen, producing softer, more holistic edge maps than Canny.
  • style.py / openclip.py — VisionModel: not a spatial map at all — a single pooled CLIP image-embedding vector, used by the style conditioning path (configs/lora/style.yaml, Lesson 8's third row) instead of depth's per-pixel map.

Which one loads is a one-line Hydra swap — compare configs/lora/encoder/midas.yaml (_target_: src.annotators.midas.DepthEstimator) against configs/lora/encoder/canny.yaml or hed.yaml — same mount point in configs/lora/struct.yaml's encoder: ??? default, a different Python class instantiated underneath. Everything downstream — mapper, DataProvider, FiLM math, layer targeting — is unchanged, because none of it was ever written to know what "depth" specifically means; it only knows tensor shapes.

14Running the repo

Hydra: how a dozen yaml files become one Python object

Concept

Every knob you've seen so far — adaption_mode, which encoder, image size, learning rate — lives in a small yaml file, not scattered through Python code. Hydra is the library that stitches many small yaml files into one merged config tree at startup, then (in this repo) turns that tree straight into live Python objects.

Three ideas make the whole system click:

  • Config groups — a folder of interchangeable yaml files, like configs/model/ holding both sd15.yaml and sdxl.yaml. Only one file from a group is active per run.
  • Defaults list — each yaml's own defaults: block says which file from each group it wants, or ??? to mean "you must supply one." An override entry lets a more specific config swap out a choice a more general one already made.
  • _target_ + instantiate — any yaml dict with a _target_ key names a real Python import path. hydra.utils.instantiate(cfg) walks the whole merged tree and actually constructs every such object, innermost first, wiring constructor arguments straight from the surrounding yaml keys.

In this repo

The root config, configs/train.yaml:1-5, declares the mandatory groups and leaves room for an experiment file to override everything:

defaults:
  - data: ???
  - model: ???
  - _self_
  - experiment: null

An experiment file, e.g. configs/experiment/train_struct_sd15.yaml:1-9, starts with # @package _global_ (its keys merge straight into the top-level config, not nested under experiment:) and picks concrete choices for every group in one place:

defaults:
  - /lora@lora.struct: struct                          # mount configs/lora/struct.yaml at cfg.lora.struct
  - override /lora/encoder@lora.struct.encoder: midas   # fill struct.yaml's encoder: ??? with midas.yaml
  - override /model: sd15
  - override /data: local

Running python train.py experiment=train_struct_sd15 (or, for sampling, exactly the README's python sample.py experiment=sample_struct pattern) tells Hydra to load that one experiment file on top of train.yaml/sample.yaml. Each individual leaf yaml carries a _target_ — configs/model/sd15.yaml:4: _target_: src.model.SD15, configs/lora/encoder/midas.yaml:4: _target_: src.annotators.midas.DepthEstimator. train.py:54's single line cfg = hydra.utils.instantiate(cfg) turns the entire merged tree of yaml into real, already-constructed SD15, DepthEstimator, and FixedStructureMapper15 instances — after that line, cfg.model genuinely is a live PyTorch module, not a dict describing one. Interpolations like midas.yaml's size: ${size} pull from the one size: value set higher up (train_struct_sd15.yaml:22: size: 512) — a single source of truth shared across model, encoder, and data config, instead of three copies that could silently drift apart.

15Running the repo

Code flow: training, step by step

Concept

With every earlier lesson's pieces named, train.py reads as a straight-line story: build the model, attach the LoRA(s), loop over the data, and every so often generate a sample image to check progress.

In this repo

  1. Compose & instantiate (train.py:33-58) — Hydra loads the config (Lesson 14), instantiate builds the real SD15 model, moved to the accelerator's device.
  2. Attach LoRAs (train.py:61, delegating to utils.py:48-112 add_lora_from_config) — for each entry under cfg.lora (here, just struct), build a fresh DataProvider, call model.add_lora_to_unet (Lesson 8's layer-swap), and optionally load an existing checkpoint.
  3. Optimizer (train.py:71-86) — one AdamW over three parameter groups: the LoRA A/B/gamma/beta weights (model.params_to_optimize), the mapper's weights, and (if unfrozen) the encoder's weights. self.unet.requires_grad_(False) from Lesson 6 means the base UNet weights never appear here.
  4. Per-step training (train.py:141-168) — pull a batch, build cs = [imgs] * n_loras (Lesson 10), call model.forward_easy(imgs, prompts, cs, ...) which internally does everything from Lessons 2, 3, 7, 9, 11, 12 in one pass, then accelerator.backward(loss) and an optimizer step.
  5. Periodic validation (train.py:179-282, every cfg.val_steps) — switch to eval mode, run real image generation (Lesson 16's sampling path) on a few held-out batches, log the generated images plus the conditioning map itself to TensorBoard, then save a checkpoint via utils.py:136-144 save_checkpoint before resuming training.
16Running the repo

Code flow: sampling, step by step

Concept

sample.py is the script the README's python sample.py experiment=... usage actually runs. It's shorter than training because there's no loss, no backward pass, no optimizer — just: load a trained checkpoint, feed it real conditioning images, save the outputs.

In this repo

  1. Compose, instantiate, load checkpoint (sample.py:41-65) — same Hydra/instantiate pattern as training, plus add_lora_from_config now actually finding a ckpt_path and loading real trained weights into the swapped-in LoRA layers and mapper (utils.py:88-104).
  2. Freeze for inference (sample.py:84-85) — unet.requires_grad_(False); unet.eval().
  3. Per-batch sampling (sample.py:94-132) — pull a conditioning image from the val dataloader, build cs = [imgs for _ in model.mappers] (Lesson 10's live-extraction trick, now on whatever reference photo you supplied), then model.sample(**pipeline_args).
  4. SD15.sample_easy (model.py:649-713) — for each conditioning source, doubles the map into a [zeros, real_map] pair (Lesson 17's classifier-free guidance), runs the encoder+mapper+DataProvider chain once, then calls self.pipe(...) — diffusers's own multi-step denoising loop, which repeatedly calls the now-patched UNet exactly as in training, just without gradients and for ~50 steps starting from pure noise.
  5. Save outputs (sample.py:131-143) — each generated image and its input conditioning image are written to disk side by side, so you can directly compare "the depth I asked for" against "the depth the output actually has."
17Running the repo

Why conditioning gets randomly dropped

Concept

If a model is always shown a prompt and always shown a depth map, it never learns what to do without them — and at generation time you often want to dial the strength of conditioning up or down, not just have it fully on. The standard fix is classifier-free guidance (CFG): during training, randomly blank out the condition some small fraction of the time, so the network also learns the "no condition" case. At generation time, run the model twice per step — once with the real condition, once with it blanked — and push the output away from the unconditioned guess and towards the conditioned one, by a tunable amount. That amount is the familiar "guidance scale" slider.

In this repo

Two independent dropout sites, both controlled by c_dropout (default 0.05, model.py:60). Text prompt dropout, model.py:380:

prompts = ["" if random.random() < self.c_dropout else p for p in prompts]

Depth-map dropout, per conditioning source, model.py:456-459:

dropout_mask = torch.rand(bsz, device=lora_c.device) < self.c_dropout
lora_c[dropout_mask] = torch.zeros_like(lora_c[dropout_mask])

At generation time, sample_custom, model.py:580-586, 626-627, builds the paired batch and combines the two predictions:

c = torch.cat([neg_c, c])   # [unconditioned copy, real conditioned copy]
...
noise_pred = noise_pred_uncond + self.guidance_scale * (noise_pred_text - noise_pred_uncond)

guidance_scale itself is a plain constructor argument (model.py:61, default 7.5) set per-experiment in configs like sample_struct.yaml:24.

19Extending to segmentation

Why SDXL, not SD1.5

Concept

Lesson 4 derived a hard rule for SD1.5: height and width must both be divisible by 64, because the VAE divides by 8 and the UNet's 4 stages add 3 more halvings (2³ = 8; 8×8 = 64). SDXL's UNet has a different shape — only 3 stages, so only 2 internal halvings — which relaxes that rule to divisible by 32 (8 × 2² = 32). That's not a cosmetic difference: a dataset whose native resolution satisfies one constraint but not the other has to be resized for one model and not the other.

In this repo

Confirmed directly from the published UNet config, not assumed: stabilityai/stable-diffusion-xl-base-1.0's unet/config.json sets block_out_channels: [320, 640, 1280] — 3 entries, not SD1.5's 4. For this session's real target resolution, 1280×800: 1280÷64=20 but 800÷64=12.5 (SD1.5 can't take it natively), while 1280÷32=40 and 800÷32=25 (SDXL can, exactly, no resize at all).

Because self.max_depth is computed generically from the loaded UNet's own config (model.py:129: len(self.pipe.unet.config["block_out_channels"]) - 1), every piece of Lesson 8's layer-patching logic already adapts automatically — no SDXL-specific branch needed there. The one real gap: this repo had no way to load a better VAE than whatever ships with the base checkpoint. Added vae_path to ModelBase.__init__ (model.py:59, 92-96), used to load madebyollin/sdxl-vae-fp16-fix — the community-standard fix for SDXL's known fp16 color/stability issues — the same mechanism the existing tiny_vae option already used for a different purpose.

20Extending to segmentation

Precomputed maps: skip_encode for real

Concept

Lesson 10's depth path is live: MiDaS runs fresh, every training step, on the same image being denoised. Segmentation flips that: SegFormer-B5 is heavier, so instead of running it every step, it runs once, offline, ahead of time, over every training image — and training just loads the finished result off disk. The architecture doesn't need to know which strategy produced the map; it only needs the map in the same shape as before.

In this repo

seg_map_calculations.py walks a dataset (several input modes: a single image, a JSONL manifest, a folder scan, or a data_dir of existing split manifests), runs SegmentationEncoder.label_ids() once per image, and saves the result as an 8-bit class-ID PNG — pixel value is the class id (0–18), not a color. Output is a standard three-field manifest:

{"raw_image_path": "...", "seg_path": "...", "prompt": "..."}

SegJsonDataset._load_seg_colormap (src/data/local_seg.py) loads that PNG at training time, resizes with NEAREST only (averaging class ids during a smoother resize would invent classes that were never there), and colourises it into the same [3, H, W]-shaped tensor a live encoder would have produced. segformer_training.py then calls model.forward_easy(..., skip_encode=True) — the exact switch documented in Lesson 16, now actually exercised for the first time by this repo's own training code, not just theorized.

21Extending to segmentation

The segmentation encoder

Concept

Two families of model can turn a photo into "what's in each part of this scene": a dense per-pixel classifier (one forward pass, every pixel gets a class), or an open-vocabulary detector-plus-segmenter like Grounded-SAM (text-prompted boxes, then a mask per box). For a fixed, well-covered taxonomy like Cityscapes' 19 driving classes, the dense classifier wins on every axis that matters here: roughly 20× faster per image (real numbers, not estimated: SAM-style mask generation runs ~1.65s/image, dense classifiers ~0.06–0.08s/image), and it handles "stuff" classes (road, sky, vegetation) natively, where box-shaped prompts struggle since those regions don't have clean rectangular extents.

In this repo

SegmentationEncoder (src/encoders/seg_encoder.py) wraps nvidia/segformer-b5-finetuned-cityscapes-1024-1024 via HuggingFace transformers, frozen, matching every other annotator's contract: [-1,1] image in. Unlike depth (Lesson 9), it does not force a square crop first — SegFormer's Mix-FFN has no fixed positional embedding, so it handles arbitrary (H, W) natively, sidestepping the pad/crop tradeoff depth's own better_resize has to make.

SEG_CITYSCAPES_PALETTE is the single source of truth for id↔colour everywhere in the pipeline — seg_colorize_ids/seg_ids_from_colormap are exact inverses of each other (verified: round-tripping random class ids through colourise-then-invert reproduces them exactly, both batched and single-image). .live_available = True marks that this particular encoder can be re-run on a freshly generated image — which is what makes Lesson 24's accuracy check possible at all.

22Extending to segmentation

A real bug, found and fixed

Concept

A parameter that's declared but never read is a sneaky bug: the function signature looks like it supports something, callers pass it in good faith, and nothing crashes — it's just silently ignored. This is exactly the kind of gap that only surfaces by tracing every call site of a flag, not by reading one method and assuming its siblings match.

In this repo

Tracing every skip_encode call site turned up exactly that. SD15.forward() (model.py:528) had the correct branch all along — the pattern every other method should have matched:

if skip_encode:
    cond = lora_c
else:
    cond = encoder(lora_c)

Three other methods declared the same parameter but never checked it — cond = encoder(c) ran unconditionally regardless of what skip_encode was set to: SDXL.forward() (model.py:852-908, used by segformer_training.py), SDXL.sample() (model.py:953-1007, used by segformer_inference.py), and SD15.sample_easy() (model.py:717-768, which didn't even declare the parameter until this fix). Harmless for training, where the placeholder encoder is torch.nn.Identity (a no-op either way) — but genuinely broken for inference, where the real SegmentationEncoder would have run again on an already-finished, already-colourised conditioning map as if it were a raw photo. All three now match SD15.forward()'s pattern exactly.

23Extending to segmentation

Two new sampling knobs

Concept

Decaying the conditioning's grip. Generation is ~50 steps (Lesson 3). Keeping the segmentation map's influence at full strength for every step can make output look flat or paint-by-numbers, once the rough layout is already settled. The fix: hold full strength while the model is still deciding the big picture, then smoothly loosen the grip in later steps so the base model's own texture knowledge can take over.

Softening hard edges. A segmentation map's class boundaries are pixel-exact — no real photo has that. Feeding the model perfectly crisp boundaries every time risks it learning to render unnaturally crisp, cartoonish edges instead of the soft transitions a camera actually sees.

In this repo

Both live on ModelBase, so any model subclass gets them for free. soften_conditioning (model.py:356) is a depthwise box blur — verified: a hard 0→1 edge comes out with genuine in-between values near the boundary, and kernel_size ≤ 1 is a true no-op.

lora_scale_schedule_callback (model.py:376) hooks into diffusers' real callback_on_step_end mechanism (confirmed its exact calling convention — callback(pipe, step_index, timestep, callback_kwargs) — by reading the installed diffusers source directly, not guessing) and reuses the same .lora_scale attribute toggle_loras() already flips between train/val (utils.py) — just varied smoothly per step instead of once per run:

frac = step_index / (num_inference_steps - 1)
scale = lora_scale_start if frac <= decay_start_frac else 
for layer in all_patched_lora_layers: layer.lora_scale = scale

When lora_scale_start == lora_scale_end, this returns None — no callback gets installed at all, so the existing depth pipeline (which never sets these) is provably unaffected.

25Extending to segmentation

Five more bugs, found by actually running it

Concept

Reading code carefully catches a lot, but some bugs only show up when tensors actually flow through the real shapes on real hardware. All five bugs below passed a plain read-through (and, for the first two, a first attempt at fixing them) before a real training step on a GPU exposed them. That's the case for smoke-testing on a small local GPU before ever touching a training cluster: it's cheap, fast failure instead of expensive, slow failure.

In this repo

1. The mapper's downsampling pyramid didn't match SDXL's UNet. src/mapper_network.py's FixedStructureMapperXL.down had only one stride-2 conv (÷2 total) before branching into per-depth outputs. The proven SD1.5 version, FixedStructureMapper15, has three (÷8 total) — matching the VAE's own ÷8 downsample, so its shallowest output lands exactly on the UNet's stage-0 latent resolution. Trimming the block count 4→3 for SDXL's 3-stage UNet was correct; also trimming self.down from 3 stride-2 convs to 1 was not — that ÷8 is VAE downsampling, independent of how many UNet stages follow. Result: the mapper's conditioning map was 4× too large at every depth, and the very first training step crashed with a tensor-shape mismatch inside src/lora.py's NewStructLoRAConv.forward(). Fixed by restoring the missing two stride-2 convs.

2. SDXL.forward() returned the wrong number of values. ModelBase's abstract signature (and SD15.forward(), which works correctly) both promise a 4-tuple: (model_pred, loss, x0, cond). SDXL.forward() only returned 3, dropping cond. Harmless as long as nothing unpacked the result — but forward_easy() (used by both train.py and segformer_training.py) always unpacks 4, so this crashed immediately after bug #1 was fixed. Fixed by returning cond (the last LoRA's pre-mapper conditioning tensor, same semantics as SD1.5) as the 4th value.

3. max_train_steps never actually stopped training. Both train.py and the new segformer_training.py compute max_train_steps only to size the tqdm progress bar — nothing ever compared global_step against it to break the loop. A run asked for 3 steps instead silently continued through the entire dataset (20 images, one gradient step each), validating — a full 50-step image generation — after every single one. Fixed in segformer_training.py by setting the existing stop_training flag once global_step >= max_train_steps (reusing the same flag the SIGUSR1 handler sets, so the loop's existing "run validation once more, then break" logic just works). The fix itself then hit a second, smaller bug: assigning to stop_training inside main() without global stop_training made Python treat the name as local for the *entire* function — breaking every earlier read of it too (UnboundLocalError). One-line fix: add the global declaration.

4. SDXL's micro-conditioning metadata was hardcoded to 1024×1024. SDXL.get_conditioning()'s compute_time_ids() always told the UNet original_size = target_size = (1024, 1024), regardless of the real training resolution. SDXL learns resolution/crop-aware behavior from this signal, so training on 1280×800 while claiming 1024×1024 is a real train/inference mismatch — not a crash, a silent quality cost, arguably worse since nothing would ever point at why. (Sampling was never affected: diffusers' own pipeline __call__ derives this correctly from the real height/width kwargs already passed in — only the hand-rolled training path had this hardcoded.) Fixed by threading the actual image size through from imgs.shape[-2:].

5. The training loop's early-stop only broke the inner loop. if stop_training: break sat inside the batch loop, but not after the outer for epoch in range(cfg.epochs) loop. With epochs=1 (every run so far) this never mattered — the outer loop only ever ran once anyway. But it's a real latent bug: epochs > 1 combined with an early max_train_steps stop would silently run one more unwanted training step into the next epoch before actually stopping. Fixed by breaking the outer loop too.

26Extending to segmentation

A full-dataset proof run: honest results, not a victory lap

Concept

A local smoke test proves the pipeline doesn't crash. It does not prove the model has learned anything -- those are different claims, and conflating them is how teams end up "sure" about things that aren't actually true. The honest version of a proof run reports what it actually shows, including the parts that are ambiguous or point at more work, not just the parts that look like a win.

In this repo

The run: 50 real training steps on the full 2975-image Cityscapes set (not the 20-image test slice), batch size 1, validation checkpoints saved as plain PNGs at step 25 and step 50 (segformer_training.py's val_grids/ folder -- added this session so results are one file-open away, not buried in a tensorboard server). Loss across all 50 steps stayed numerically stable (no NaN, no explosion) but stayed noisy throughout (bounced between ~0.003 and ~0.33) -- expected, not concerning, for batch size 1 with a random denoising timestep sampled every step; single-sample loss variance is dominated by which timestep got picked, not by whether learning is happening.

The honest finding: step 25 and step 50 used the identical seg map and the identical fixed seed -- a genuine controlled A/B, since only the LoRA weights differ between them. Step 25's output was a coherent, colourful street photo with plausible structural alignment. Step 50's output shifted to a sepia/vintage photograph tone with visible watermark-like caption text at the bottom -- a real, unexpected change, not something to gloss over. Loss didn't spike at that point, so this isn't training divergence in the numerical sense; the likelier explanation is SDXL's own base model drifting toward one of its learned "vintage stock photo" style basins as the still-noisy LoRA weights shift the conditioning -- base SDXL was trained on a huge, uncurated web dataset that includes plenty of watermarked archival photos, a well-known base-model quirk. This does not establish whether segmentation-conditioning itself is improving or not: that needs averaging over several seg maps, not one seed on one image.

A second real bug, found by testing the fix. To test whether a negative prompt suppresses the watermark artifact, running segformer_inference.py against the step-50 checkpoint (offline, local_files_only=true) hit an immediate crash: cfg.model.vae_path defaults to the hub id string "madebyollin/sdxl-vae-fp16-fix", and the offline-path-resolution block naively did os.path.join(_root, cfg.model.vae_path) -- joining the repo root with a hub id, not a real local folder, producing a path that obviously doesn't exist. This is the same category of gap already fixed in segformer_training.py (Lesson 25) -- it just hadn't been hit yet because inference had never actually been run this session. Fixed the same way: a dedicated vae_local_path key in configs/inference_seg.yaml pointing at the real checkpoints/local_models/sdxl-vae-fp16-fix folder, resolved instead of the hub-id string when local_files_only=true.

A third, once the second was fixed: guidance_scale collided with itself. segformer_inference.py explicitly passes guidance_scale=cfg.inference.get("guidance_scale", 7.5) into model.sample() so that config knob actually does something -- but SDXL.sample() also hardcoded guidance_scale=self.guidance_scale (the model's own fixed instance attribute) in its final call to the underlying diffusers pipeline, while separately forwarding **kwargs -- which still contained the caller's guidance_scale. Python: got multiple values for keyword argument 'guidance_scale'. This exact call path -- segformer_inference.py calling SDXL.sample() -- had never actually executed before tonight; segformer_training.py's validation calls never hit it because they don't pass guidance_scale explicitly. Fixed by resolving one guidance_scale value up front (caller's, if given, else the model's default) and using it consistently for both the per-LoRA CFG-doubling decision and the final pipe call -- not just silencing the crash, since those two needing to agree is the actual point of the variable.

A fourth: the checkpoint itself is internally dtype-inconsistent. With #2 and #3 fixed, inference crashed a third time, this time deep inside stock diffusers code (UNet2DConditionModel.forward → TimestepEmbedding → linear_1) with RuntimeError: mat1 and mat2 must have the same dtype, but got Half and Float. Checked the actual downloaded files directly (safetensors' get_slice(...).get_dtype(), not a guess): checkpoints/local_models/stable-diffusion-xl-base-1.0's UNet and VAE are F32, but both text encoders are F16 -- stabilityai/stable-diffusion-xl-base-1.0's default (non-"fp16"-variant) files ship that way, and download_models.py never requested an explicit torch_dtype, so each component kept whatever precision its own file happened to be saved at. Training's forward() never hit this because it builds every tensor itself, always at a consistent dtype; sample()'s call into the stock pipeline infers a working dtype from the (fp16) text embeddings and casts latents to match, feeding fp16 latents into the fp32 UNet. Fixed at the root in ModelBase.__init__ (src/model.py): self.pipe.to(dtype=torch.float32) right after the pipeline loads, so every model instance -- training or inference -- starts from one consistent dtype regardless of what a given checkpoint happens to ship as.

A fifth, once the fourth was fixed: a missing height/width on the second of two near-identical calls. The "RAW SEG GEN" (empty-prompt) panel's model.sample() call was missing the same explicit height=size_h, width=size_w the first call has -- so it silently fell back to SDXL's default square size while the conditioning tensor stayed built for the real 1280x800 shape, crashing inside NewStructLoRAConv.forward() with the same kind of shape-mismatch error as bug #1, just different numbers. Copy-paste-adjacent code with one path exercised and the other not is exactly where this kind of thing hides. Fixed by matching the first call.

Five real bugs in one investigation, each only reachable by fixing the one before it and actually running the result. None of them were visible from reading the code in isolation. This is the argument for the smoke-test discipline this whole extension was built on: run it for real, on real hardware, before trusting it.

A full re-run, and a dormant bug found by testing the sibling branch

Concept

Two ideas from earlier lessons combined into one real finding this session. Lesson 25's whole argument is that some bugs only show up by actually running the code, not by re-reading it. Separately, this project's decision log has always said a bug in shared code shows up on whichever branch's data happens to exercise it first, and can sit dormant on the other branch indefinitely. In this repo

Config through instantiation, real, not assumed: hydra.compose(config_name="train", overrides=["experiment=train_seg"]) still resolves cleanly; hydra.utils.instantiate() on the mapper still produces exactly 1,222,048 parameters, unchanged from Lesson 18's number despite every config rewrite since. The dormant bug: segformer_inference.py's own _load_seg_map() calls seg_colorize_ids(ids, palette) with no bounds check on ids -- a raw palette[ids] lookup, same shape as the bug Lesson 24 already found and fixed in src/data/local_seg.py's training-side loader. It never crashes on this branch's own data, because SegFormer's dense classifier always predicts one of its 19 real classes -- IGNORE_ID (255) never appears in a map this branch produces. The practical lesson: "this branch's data can't trigger this" is true today and was never actually false -- but it's also not a reason to leave the same unguarded pattern sitting in a second copy of the same function, when the sibling branch already paid the cost of finding out what happens when the assumption doesn't hold.

29Extending to segmentation

Colorizing class IDs to RGB was a shortcut, not a design choice

Concept

Segmentation classes are categorical, not continuous. Feeding a palette-colorized RGB image through a normal conv stem (FixedStructureMapperXL, unchanged from the original repo's depth-conditioning mapper) forces the network to re-derive "this shade of blue means sky" from raw pixel values -- and two classes assigned nearby palette colors become harder to tell apart than they should be, an unforced information bottleneck. The standard approach for semantic-image-synthesis (SPADE, OASIS, and most segmentation-to-image diffusion work) is a learned embedding table: each class gets its own vector directly, no color round-trip. That's also exactly what NewStructLoRAConv's gamma/beta FiLM modulation is built to consume.

In this repo

What changed: a new SegIDStructureMapperXL (src/mapper_network.py) replaces FixedStructureMapperXL as this branch's default mapper. It takes the raw class-id map directly (Long [B,H,W]) through an nn.Embedding stem plus a cheap derived boundary channel (min/max-pool trick, no extra data needed), instead of colorizing to RGB first and running a 3-channel conv stem over it. Mirrors mask2former branch's own SegStructureMapperXL, which used this approach from the start -- this branch (and grounded_sam) are catching up to it, not inventing something new.

The one subtlety that would have been a silent bug: src/model.py's CFG dropout zeroes a whole sample's conditioning tensor directly -- c[dropout_mask] = 0 -- before the mapper ever runs. For a colorized RGB tensor, zero is a legitimate color (black) and already meant "no signal." For a raw class-id tensor, zero is also a real class id (id 0 = "road" in this branch's scheme) -- so without a fix, CFG dropout would have silently told the model "this pixel is road" instead of "no conditioning here," for every dropped sample. Fixed by reserving id 0 as NULL: the dataset loader shifts real ids 0..18 to 1..19 at load time, and nn.Embedding(..., padding_idx=0) makes that row a true, always-zero vector -- so the existing dropout code keeps meaning exactly what it always meant, with no change needed there.

What did NOT need to change: seg_map_calculations.py was already saving raw class-id PNGs, not colorized ones -- colorization only ever happened at dataset-load time. So the precompute pipeline needed zero changes; only the dataset loader (src/data/local_seg.py, new conditioning: "classid"|"rgb" switch, default classid) and segformer_inference.py's conditioning path (kept the colorized version around separately, for the display grid panel only) needed updates.

Verified, not just written: a real 8-step training run (batch_size=1, 1280x800, the real 20-image dev slice) completed with no crash -- loss stayed numerically sane (0.24 → 0.149 → 0.0056 → ... → 0.0024, noisy but no NaN), a validation pass ran, and real checkpoints (lora-checkpoint.pt, mapper-checkpoint.pt) plus real generated grid images landed on disk at outputs/train/seg/runs/2026-08-25/07-02-19/. This confirms the mechanism is wired correctly end to end -- embedding lookup, boundary derivation, and the CFG-dropout-to-NULL-id interaction all behaved as designed. It does not yet say anything about generation quality: 8 steps is a wiring check, not a convergence claim.

30Extending to segmentation

One prompt for 150 images is barely a prompt at all

Concept

A text prompt only teaches the model something if it varies with what's actually in the image. A prompt that's identical across ~150 images (one per Cityscapes city) carries almost no information the model can learn from -- it's closer to a constant bias than real supervision. This repo's own config comments already called this out: configs/experiment/train_seg.yaml flags that "a vague prompt lets the base model's own prior dominate the structure signal," a real risk for a project whose entire point is measuring how well the LoRA follows the STRUCTURE signal.

In this repo

enrich_prompts.py (new) walks a folder for every *.jsonl manifest, runs a local BLIP captioning model over each referenced image, and replaces the generic template with a real per-image caption. This doesn't fight the segmentation-conditioning goal: BLIP describes scene CONTENT ("cars driving down a street in front of a tall building"), not precise spatial layout -- the text encoder gets something real to key off, while the segmentation map stays the only signal carrying WHERE things are. Reversible by construction: a one-time .bak copy per file before the first write, plus a prompt_original field kept on every entry, so nothing is silently lost even without opening the backup.

Verified, not just written: ran for real against this branch's own dev manifest -- 6/6 entries enriched, each getting a genuinely distinct caption instead of the shared template, confirmed both via a live first-time download and again fully offline against the local checkpoints/local_models/blip-image-captioning-large copy. Sample: "a photo of a city street in aachen" → "cars driving down a street in front of a tall building".
